# L9 frozen repository benchmark

This corpus is frozen before L9 implementation or Lattice benchmark-output inspection. Repository pins are in `repositories.json`; six core question sets and source-derived reference answers are in `core/`, with the common questions and representative actions in `core-questions.json`. The other six question sets and answers are in `extra-reference.json`; `extra-questions.json` is the answer-free evaluation packet. Source permalinks identify the exact commit and lines. Questions and pins must not be edited after the freeze commit. Corrections require separately labelled errata preserving the original and cannot silently change a score.

## Measurements fixed before implementation

- Analyze the complete tracked checkout at each pin, with no lens, AI summary, or benchmark-specific configuration. LFS binary assets need not be downloaded; preserve their tracked paths. Do not execute repository application/build scripts as part of Lattice analysis.
- Product coverage is the union of product source-file IDs reachable through all initially offered package/folder boxes, including folded descendants, divided by an independent tracked-source inventory. Exclude test/test-fixture, vendor/third-party, generated and build-output categories only when supported by path/build metadata; retain `src/main`. Record exclusions and unsupported files separately. Required coverage is90% per repository, not an average hiding a failed repository.
- Manifest dependency recall compares directed internal package pairs, retaining normal/dev/optional/conditional scopes as separate evidence. Cargo metadata is an independent oracle; Gradle declarative source inventory is provisional until evaluated project dependencies are available. Never label an unavailable oracle as95% pass. Empty denominators are N/A. Report recall per ecosystem/repository and aggregate;95% is required for each nonempty verified denominator.
- Time the full cold-cache build, from process start to persisted complete graph, with hardware, OS, Node version, exact source/tool commits and resource use recorded. Whole large checkout must contain at least10,000 tracked files; timeout300seconds is a failure, not a successful partial graph. Report warm build separately.
- First meaningful map timing: installed Chrome, fresh context/browser, disabled HTTP cache, blocked service workers, gzip loopback HTTP, no artificial network throttling.390×844 at CPU4×, exactly three valid samples, median <=2seconds per repository.1440×900 at CPU1× provides desktop evidence. Ready means visible real package/folder boxes and dependency summary after two animation frames, not a spinner or skeleton. Record all samples, payload sizes, console errors, overflow and failures. Public-network timings are separate observations.
- On the large map, capture a browser performance trace for package expansion, node selection and flow navigation. Report maximum task and input-to-next-paint times plus visible truncation/pagination. Do not describe a frozen or nonresponsive view as passing merely because initial load is fast.

## Conservative call audit

Sample50 `exact` emitted call edges across supported language families after sorting by language/path/callsite/target. Rank by SHA256 of `L9-v1:81:` plus that identity. Allocate seven each to JS/TS, Python, Go, Rust, Java/Kotlin and C#, then eight from the remaining ranked pool. A shortage is recorded and allocated across the remaining pool; fewer than50 total is insufficient evidence. Inspect caller expression, lexical binding and callee definition from pinned source independently of extractor claims. Ambiguous/unproven target counts as incorrect. At least48/50 must be correct. Separately inspect estimated calls, never combine their count with exact-call precision.

For recall, a source-only reviewer records the first five explicit internal call sites in the fixed representative entry/flow source spans for each supported repository before inspecting extracted call edges. Preserve unsupported, callback, virtual and external classifications; report exact matched/eligible counts and the bounded sample denominator. This is sampled recall, never whole-repository recall. Repository code and dynamic dispatch are not executed to manufacture call truth.

## Blind questions and comparison

Each repository has four fixed questions. Use fresh agents with no implementation history. The Lattice lane may inspect map images, navigate the generated map and call its MCP tools, but must not open source checkouts, reference-answer files, external repository pages or source URLs. Grounded snippets returned by the map/MCP are allowed evidence. A separate fresh source-only agent gets the same questions and pinned source, without Lattice output or the reference answers. Give both lanes the same ten-minute time limit, record available tools and all answer artifacts. This is an agent comparison, not a measured human usability claim.

A separate grader compares answers against frozen source answers: each question0(absent/wrong),1(partly correct without invented claims),2(core facts and evidence), total0–8 per repository. Unsupported claims lose evidence credit. Report question-level scores, omissions and any advantage/disadvantage; no unstated score threshold is substituted for the user's final judgment. Unsupported C/C++ is a negative capability control: honest limits are correct; invented calls are failures.
