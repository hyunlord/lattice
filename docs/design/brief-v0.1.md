# Astra 의뢰서 — Lattice v0: 저장소의 "시스템 지도"를 계속 갱신하는 범용 도구 (CLI + 웹 뷰어 + MCP)

작성 2026-10-10 · v0.1: 첨부 시제품의 역할을 명확히 하고 범용 뷰어 명세 추가 · 새 저장소 `hyunlord/lattice` · 이 일은 이 세션만 하는 **오래 도는 목표(goal)**다. 가칭은 바꿔도 된다(바꾸면 ADR에 기록).

## 무엇을 만드나
Graft가 코드의 **호출 구조**를 그래프로 만들어 에이전트에게 주듯, Lattice는 저장소의 **시스템 구조**를 그래프로 만든다. 제품이 어떤 개체(콘텐츠·시스템·데이터·모듈)로 이루어져 있고, 서로 무엇을 주고받으며, **설계 의도와 실제 구현이 어디서 어긋나는지**를 보여 준다.

- 코드·데이터가 바뀔 때마다 자동으로 다시 만들어진다.
- 사람은 **웹**에서 보고, 에이전트(Claude Code·Codex·Astra)는 **MCP**로 묻는다. 둘이 보는 그래프는 같다.
- **어떤 저장소에서도** 쓸 수 있다. 핵심은 게임을 모른다. 의미는 저장소마다 두는 설정(렌즈)이 붙인다.

첫 사용처는 `hyunlord/bs-mobile`이다. Claude가 그 저장소의 `data/`에서 시제품 "Sow & Siege 시스템 지도"(정적 HTML, 첨부)를 손으로 뽑았다.

### 첨부 시제품을 어떻게 쓰나
- **쓰는 것: 내용의 정답.** 집계 수치, 분류 규칙(시제품 각주), 발견 문장, "설계 의도 대 실제 동작" 비교라는 관점. Lattice는 bs-mobile 렌즈만으로 이 내용을 재현해야 한다.
- **쓰지 않는 것: 화면 구조와 모양.** 시제품은 bs-mobile 한 저장소를 위해 손으로 짠 일회성 페이지다. 탭 이름(무기·도구·판 밖 성장), 고정된 순환 도식, 하드코딩된 발견 카드, 게임 아트에서 가져온 색은 **범용 도구의 양식이 아니다.** 그대로 옮기지 말고, 아래 "L2 범용 뷰어 명세"에 맞춰 **어떤 저장소가 와도 성립하는 정보 구조**로 다시 설계한다. 시제품의 각 보기는 그 구조 위에서 "bs-mobile 렌즈가 켠 보기"로 나와야 한다.
- 판단 기준: 게임이 아닌 저장소(예: 웹 서비스 백엔드, 데이터 파이프라인)에 렌즈 없이 돌렸을 때도 각 화면이 빈 껍데기가 아니라 의미 있는 내용으로 채워지는가.

## 참고: Graft (trailhq/Graft, MIT, TypeScript)
가져올 것: 결정론적 1단계 추출(모델 없이) / 내용 해시 기반 캐시와 질의 전 신선도 검사(수 ms, 바뀐 것만 다시) / 저장소 안 재생성 가능한 캐시 폴더(gitignore) / `init`으로 AGENTS.md 구역·Claude Code 스킬·`.mcp.json`·Codex 설정 연결 / `viz` 로컬 뷰어와 정적 내보내기 / 신선도 확인 MCP 도구.
**다른 점**: Graft는 심볼·호출이 단위다. Lattice의 단위는 **개체·관계·의도 대 구현**이다. 코드 쪽 정보가 필요하면 Graft 그래프(`graft/.graph/wiring.json`)가 있을 때 **읽어서 쓰고**, 없으면 최소한의 자체 추출로 대신한다. Graft 코드를 복사하지 않는다.

## 설계 원칙
1. **핵심은 범용, 의미는 렌즈.** 코어에 "무기·도구" 같은 단어 금지. 렌즈 없이도(설정 0) 쓸모 있는 지도가 나와야 한다.
2. **결정론.** 같은 입력이면 같은 그래프 해시. LLM 단계는 v0 범위 밖.
3. **사람과 에이전트가 같은 것을 본다.** 웹 뷰와 MCP 응답은 같은 그래프·같은 발견(findings)에서 나온다.
4. **변화가 일급.** 커밋 사이의 "시스템 차이"(무엇이 생기고 사라지고, 구현 깊이가 어떻게 바뀌었나)를 언제든 볼 수 있다.
5. **규칙은 검사가 된다.** 렌즈의 발견 규칙은 CI 관문으로도 돌 수 있다.

## L0. 설계 (짧게)
`docs/design/lattice-v0.md` + ADR 몇 개.
- **그래프 모델**: 노드(id, kind, name, 속성, 출처 파일:줄, 내용 해시), 간선(종류, 방향, 출처 필드), 면(facet: 렌즈가 붙이는 분류. 예: 구현 깊이), 발견(finding: 규칙 id, 대상, 수치, 문장).
- **추출기(adapter)**: ① 데이터 레코드(JSON·YAML·CSV, 이후 Unity 직렬화 YAML) ② 마크다운 문서(제목·링크·ADR) ③ 코드(Graft 그래프 가져오기 / 없으면 파일·모듈 단위 최소 추출) ④ 저장소 메타(git 커밋·경로).
- **참조 자동 해석**: 어떤 필드 값이 알려진 노드 id와 같으면 간선을 만든다(간선 이름 = 필드 경로). 렌즈 없이도 데이터끼리의 연결이 보이게.
- **렌즈 스키마**(`.lattice/lens.yaml`, 필요하면 `.lattice/lens.ts`로 확장): 개체 종류(파일 패턴·id 필드·이름 필드·보여 줄 필드), 간선 규칙, 면 분류 규칙(식), 보기 정의(행렬·순환 도식·분포), 발견 규칙(질의 + 문장 틀 + 선택적 관문 임계값), **코드 연결 규칙**(예: 데이터의 `operation` 값이 코드의 어떤 처리기에 실제로 있는지 → "구현됨/설계만" 판정).
- **저장**: `.lattice/cache/`(gitignore) 그래프 + 입력 지문, 커밋별 스냅숏(차이 계산용).

## L1. 코어 + CLI
- `lattice init` (렌즈 뼈대 생성 + 에이전트 연결은 L3)
- `lattice build` (증분, 지문 비교로 바뀐 것만)
- `lattice check` (발견 규칙 중 관문 지정된 것 평가, 실패 시 종료 코드 1)
- `lattice diff <ref>` (시스템 차이: 노드·간선·면·발견의 추가/삭제/변경)
- `lattice export <dir>` (정적 사이트 + 그래프 JSON)
- `lattice serve` (로컬 뷰어, 파일 감시로 자동 갱신)
- 언어: TypeScript(strict), Node LTS, npm 패키지. 테스트·형식·타입 검사 CI.

## L2. 범용 웹 뷰어
정적 SPA, 서버 없이 `export` 결과만으로 동작. **화면은 범용 모델(종류·간선·면·발견·보기·스냅숏)에서만 그린다.** 특정 도메인을 아는 화면 코드는 금지. 도메인 의미는 렌즈가 준 이름·설명·보기 정의로만 들어온다.

### 정보 구조 (모든 저장소 공통)
| 화면 | 렌즈 없이 | 렌즈가 있으면 |
|---|---|---|
| **홈** | 저장소 이름·기준 커밋·신선도, 종류별 개수, 자동 발견(고립 노드, 끊긴 참조, 가장 많이 연결된 허브, 최근 변화가 큰 영역) | + 렌즈 면 분포 막대, 렌즈 발견 카드(관문 여부 표시) |
| **탐색(관계망)** | 자동 참조 간선·코드 모듈 의존으로 그린 그래프. 종류 필터, 이웃만 보기, 경로 찾기 | + 렌즈 간선 이름·색, 면으로 모양 구분, 허브 고정 |
| **목록** | 종류별 표. 열 = 레코드에서 자주 나오는 필드 자동 선택, 검색·정렬·필터 | + 렌즈가 지정한 열, "의도 대 구현" 같은 비교 열 |
| **보기** | 자동 보기 2개: 종류 × 종류 연결 행렬, 필드 값 분포 | + 렌즈 정의 보기(행렬·순환 도식·분포·표) |
| **변화** | 커밋 목록, 두 스냅숏의 노드·간선 추가·삭제·변경, 면 분포의 시간 추이 | + 발견 변화(새로 생긴 위반, 해소된 위반) |
| **노드 상세**(고정 주소) | 속성, 출처 파일:줄(저장소 링크), 들어오고 나가는 간선, 이 노드가 바뀐 커밋 | + 렌즈 면, 관련 발견, 의도·구현 비교 |

- 모든 노드·보기·변화에 **고정 주소**가 있어, 사람과 에이전트가 링크로 같은 화면을 가리킬 수 있다(MCP 응답에 링크 포함).
- 큰 저장소 대비: 노드 수천 개에서도 관계망은 집계(종류·폴더 단위로 묶기) → 펼치기 방식으로 동작.

### 시각 디자인
- **도구 자체의 중립적인 디자인 시스템**을 만든다(색 토큰, 글꼴, 간격, 컴포넌트). 개발자 도구답게 정보 밀도 우선, 장식 최소. 밝은·어두운 테마, 휴대폰 폭, 키보드 접근.
- 종류 색은 색맹 대비 검증된 팔레트에서 순서대로 배정하고, **색만으로 구분하지 않는다**(모양·라벨 병행). 상태색(관문 실패 등)은 종류 색과 겹치지 않게 예약.
- 렌즈가 바꿀 수 있는 것은 이름·설명·종류 순서·강조색 하나 정도. 레이아웃은 바꿀 수 없다.
- `docs/design/viewer.md`에 화면 와이어프레임(텍스트 또는 그림)과 디자인 토큰을 먼저 쓰고 구현한다.

### 관문
렌즈 없는 저장소, bs-mobile 렌즈, Charter & Kin 예시 렌즈 세 경우의 홈·탐색·목록·보기·변화·노드 상세 화면 캡처를 PR에 붙인다. 세 경우 모두 빈 화면 없이 의미 있는 내용이 나와야 한다.

## L3. MCP 서버 + 에이전트 연결
stdio MCP. 모든 도구는 호출 전에 신선도를 확인하고 필요하면 증분 재구성.
- `lattice_overview` — 종류·면 분포와 발견 요약
- `lattice_find` — 종류·태그·면·텍스트로 노드 찾기
- `lattice_node` — 노드 상세 + 이웃 + 출처
- `lattice_trace` — 두 노드 사이 경로, 또는 한 노드에서 n단계 영향 범위
- `lattice_matrix` — 렌즈 행렬 하나
- `lattice_findings` — 발견 목록(관문 여부 포함)
- `lattice_diff` — 기준 커밋 대비 시스템 차이
- `lattice_freshness` — 지도가 코드보다 낡았는지
`lattice init`이 AGENTS.md에 Lattice 구역, `.claude/skills/lattice/SKILL.md`, `.mcp.json`, Codex 설정(`--no-global` 지원)을 쓴다. Graft와 함께 깔려 있어도 충돌하지 않게. 스킬 문서는 "설계·구현 전에 lattice로 현재 구조와 발견을 확인하고, 작업 후 diff로 의도대로 바뀌었는지 확인한다"는 사용 절차를 담는다.

## L4. 지속 갱신 (CI)
- 재사용 가능한 GitHub Action(`lattice-action`): 빌드 → check → export → **GitHub Pages 게시**(기본 브랜치) → PR에는 **시스템 차이 요약을 댓글로**.
- Pages를 못 쓰는 저장소(비공개 무료 계정 등)는 Actions 아티팩트로 내보내고, 로컬 `serve`로 본다. 이 한계를 문서에 명시.

## L5. 실사용 검증 (관문)
1. **bs-mobile**: `.lattice/lens.yaml`만으로 첨부 시제품의 **수치와 발견 내용을** 재현한다(화면 모양은 L2 범용 명세를 따른다) — 콘텐츠 216, 첫 플레이 가능판에서 동작 77, 고유 동작 20, 물품 30 중 수치만 24, 무기 형태 4종, 챕터 보스 1종, 자재 4종을 전부 요구하는 소비처 10/10. 분류 규칙은 시제품 각주와 같게. 코드 연결 규칙으로 "런타임 operation이 C# 처리기에 실제로 있는지"도 판정해 시제품보다 한 단계 정확하게.
   bs-mobile에 PR로 렌즈와 Action을 넣고, Pages 링크를 보고한다. bs-mobile 쪽 의뢰서의 D1(지도 도구)은 이것으로 대체한다.
2. **범용성**: ① `hyunlord/feudal-lord-simulator`(TypeScript, 콘텐츠 데이터)에 최소 렌즈로 지도를 만든다(**읽기만, 그 저장소에 커밋·푸시 금지**. 렌즈는 Lattice 저장소의 `examples/`에). ② 렌즈 없는 공개 저장소 하나(예: 중간 규모 TypeScript 또는 Python 프로젝트)에서 설정 0으로 쓸모 있는 지도가 나오는지. **코어 코드 수정 없이** 세 저장소가 돌아야 한다.
3. **성능**: bs-mobile 기준 전체 빌드 10초 이내, 변경 없을 때 신선도 확인 50ms 이내, MCP 응답 1초 이내. 상시 계측.
4. **결정론**: 같은 커밋 두 번 빌드 → 같은 그래프 해시.
5. **에이전트 사용 확인**: Claude Code와 Codex 각각에서 MCP 도구 목록이 보이고, "물품 중 수치만인 것과 그 설계 의도"를 MCP로 물어 정답이 나오는 기록.

## 하지 않을 것 (v0)
LLM 요약 단계, 뷰어에서 데이터 편집, 다중 사용자 호스팅·인증, Graft 코드 복제.
