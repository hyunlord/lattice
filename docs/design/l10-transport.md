# L10 bounded packed transport

The canonical cache graph and graph hash are unchanged. Data packs use gzip level 9. Static export and each immutable live generation use the same version-2 transport writer. This is an artifact encoding, not another analysis model. No model, service API, repository-name branch, or dependency was added.

## Files and version dispatch

`overview.json`, `presentation.json`, `snapshots.json`, media and viewer assets remain ordinary files. The first overview does not request the transport index or import its decoder. `graph.json` and `snapshots/<id>.json` are small manifests containing `transportVersion: 2`, the virtual `document` path, original `hash`, full `repository`, `lensDigest`, and collection counts. Consumers that only inspect commit/hash can continue reading these directly.

`transport.json` contains `transportVersion: 2`, `indexEncoding: "gzip"`, `packPageSize: 256`, `packCount`, and `fileCount`. The index encoding field is optional for legacy version-2 exports; absent means ordinary JSON. New index files append `.gz` to each name below and satisfy the same encoded and decoded 256KiB limit as packs. A reader hashes the virtual path with the existing unsigned multiply-by-31 bucket convention. `transport/files-<two-hex-digits>.json` contains sorted inclusive path ranges, each pointing to a bounded `transport/files-<bucket>-<page>.json` array of `[path, reference]` rows. `transport/packs-<page>.json` contains at most 256 pack paths in ordinal order.

The reserved `records/<pack>/<record>/<label>.json` namespace addresses a canonical record directly through its pack ordinal and record index, avoiding a separate file-catalogue row. Labels are opaque to transport; evidence labels are the logical source-page SHA-256 and are additionally verified by the evidence reader. Direct references use the same pack bounds, hash, cycle and ordinal validation as indexed artifacts. Producers reject attempts to register virtual files under this reserved namespace.

The browser `createPackedLoader(base, suffix)` exposes asynchronous `json(path)` and `text(path)`. `readPackedArtifact(directory, path)` is its synchronous Node counterpart for offline tools. Only a 404 for `transport.json` selects legacy ordinary JSON. Invalid manifests, missing records, HTTP failures and corrupt data fail visibly; they do not select another graph. The new viewer can read old exports. Old viewers do not decode new manifests.

## Records and bounds

A pack is a gzip-compressed JSON array at `packs/<sha256-of-compressed-bytes>.json.gz`. Both compressed bytes and decompressed UTF-8 bytes are at most 262,144 bytes. The producer targets 240,000 bytes, leaving room for incompressible gzip framing. Node's built-in gzip and the browser's `DecompressionStream('gzip')` perform compression/decompression. Serve these gzip files as binary files without adding HTTP `Content-Encoding: gzip`; the loader decompresses the stored artifact itself.

A reference is `["r", packOrdinal, recordIndex]`. Scalar JSON values remain scalars; arrays use `["a", values]`, objects use `["o", [[key, value], ...]]`. Declared canonical record IDs are interned as scalars and may also be referenced as object keys; decoded keys must be unique strings. IDs are registered before traversal, while arbitrary prose, source hashes and paths retain normal local gzip compression. This explicit tagging preserves literal arrays, reserved-looking object keys and own `__proto__` fields. `["j", references]` joins string fragments, parses the resulting encoded JSON, then decodes it. Oversized records split at surrogate-safe boundaries before packing. `["s", value]` remains readable for legacy embedded JSON strings. New producers keep arbitrary strings byte-exact instead of parsing and reserializing JSON-looking text.

Arrays and objects larger than 256 entries use `["c", references]` and `["m", references]` to concatenate array chunks or merge disjoint object chunks. This bounds encoding of large collections without retaining an entire encoded graph root. Duplicate object keys remain invalid across chunks.

ID-bearing records factor stable fields, attributes and sources into independently shared object chunks. Full graph records and thin detail variants share unchanged fields while excluded attributes and provenance are never decoded or requested by the thin variant. Exact graph records and exact source records are interned by the SHA-256 of their encoded payload. Records retain source paths, pointers, lines, revisions, URLs, content hashes, attributes and order. Equal semantic graph hashes do not authorize aliasing different repository/snapshot bindings. Root graph metadata is retained independently, and changed source revision/URL creates a distinct record. Repeated exact/all logic adjacency payloads and repeated snapshot records can therefore share storage without changing the query result.

The writer keeps only one pending pack and spills the virtual-file catalogue into 256 temporary buckets. It does not concatenate a full canonical graph JSON document. Container chunks are flushed incrementally. The SHA-256 digest-to-numeric-reference table and pack catalogue still grow with the number of unique records and packs; their peak memory must be measured on the frozen large corpus. Gzip size savings alone are not acceptance evidence.

## Structured details

New packed detail indexes declare `detailVersion: 2`. Logical records remain structured values through canonical interning; physical pack fragmentation handles oversized attributes and provenance. Each bound packet contains at most 32 logical records. References use `{record: ordinal}`; packet number is `floor(ordinal / 32)` under the validated index lookup root, and the record key is the decimal ordinal. The reader also accepts prior structured single-part references. Compact lookup rows are `[0, nodeId, reference]`, `[1, [layer, kind, originalIdOrId], reference]`, or `[2, nodeId, reference]` for ID, cross-snapshot identity and label respectively. Legacy lookup maps remain readable; malformed kinds, duplicate keys and invalid references fail before record access. The reader retains support for legacy string-fragment detail packets. Compact detail collections omit repeated repository metadata and empty arrays; reconstruction supplies metadata from the validated detail index. Evidence-bearing edges, facets and findings retain ordered source groups with 128-source pages. Sources are fetched when evidence is opened. New source pages and logic node/call pages use direct canonical record addresses, avoiding thousands of tiny virtual file catalogue entries. Snapshot detail indexes preserve their own repository commit and graph binding.

## Integrity and publication

Before publishing `transport.json`, the writer rereads persisted packs, verifies their compressed-byte SHA-256, bounds decompression and checks direct reference ordinals. Construction produces references only to existing records; fragmented encoded values are assembled from those validated records. Static export retains its staging/backup/rename transaction, so a snapshot or pack failure leaves the prior site intact. The live worker finishes the same store before publishing a generation; retained generations keep their own ordinal catalogues and source-bound documents.

Readers bound both fetched and decompressed pack bytes, verify compressed SHA-256, check tags/indices, reject cycles and prototype-key duplicates, and retain at most 32 cached index/pack responses per loader. Failed requests are evicted for retry. Browser hashing uses SubtleCrypto when available and a locally implemented SHA-256 fallback for ordinary HTTP; padding-boundary and maximum-pack tests compare the fallback with Node crypto. The existing detail/logic/overview parsers continue validating reconstructed graph/repository binding and requested record identity. Generation suffixes apply to every pack/index request.

## Navigation and validation

The initial overview remains separate from packed artifacts. A projected-out default function has a source-bound focus packet. A different selected function loads its own bounded exact incoming/outgoing call pages from the existing logic transport and builds its own focus model. Displayed/total call counts disclose truncation; following a neighbor does not silently reuse that neighbor's incomplete relation list from the prior card.

Regression coverage includes HTTP and offline roundtrips, source binding with equal semantic graph hashes, oversized Unicode, content-address corruption and retry, missing-pack publication failure, old export fallback, lazy evidence ordering, exact query parity, snapshot tampering rollback, retained live generations, worker responsiveness and clean shutdown. The frozen L10 byte budgets, first-display comparison and large-corpus memory/runtime gates remain separate measurements; small fixtures do not establish those gates.

## Compressed viewer modules

The data-only compression experiments did not meet the fixed small-repository density gate. The viewer's common JavaScript is therefore also exported as deterministic gzip JSON archives with the same256KiB encoded and decoded limit. Build-time TypeScript AST rewriting maps static imports, re-exports and literal dynamic imports to stable module identifiers. This uses the existing compiler dependency; it does not add a bundler or runtime dependency.

The external bootstrap validates hashes, sizes and module identities before installing one import map and loading the application through native ES modules backed by Blob URLs. Native module cycles, live bindings and deferred dynamic-module execution must remain intact. All code archives are downloaded initially so their Blob URLs can be registered; this is eager code download, not eager graph, details or evidence loading. Paired mobile first-display measurements remain an acceptance gate.

This mode requires native import maps and gzip DecompressionStream support. A deployment CSP must allow the generated import map and Blob module URLs; the exporter must not alter or weaken a supplied policy and does not require unsafe-eval. Unsupported features or blocked loads must produce a visible failure. Network/archive validation failures may retry before map installation; failures after installation require a page reload. Compatibility and corruption fixtures plus real HTTP navigation must pass before delivery.
