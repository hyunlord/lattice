# L10 resident query and freshness state

MCP retains indexes only for the immutable graph object belonging to one verified source generation. Layer scopes, incident edges, node identities and overview facet distributions are resident. A rebuild replaces the graph object; old indexes become unreachable. The logic query index follows the same generation boundary. No time-to-live or watcher event is evidence of freshness.

`freshness.mode: content-hash` describes the graph's binding to previously read source bytes. `freshness.observationMode` separately reports whether the current observation uses `content-hash` reads or `metadata-witness` reuse. The latter does **not** claim that all bytes were rehashed on this request.

On local APFS, ext and Btrfs, previously verified bytes may be reused only when bigint device, inode, size, mtime and ctime match. Restoring mtime does not restore ctime. Initial reads verify the opened descriptor before and after hashing; path identity is checked again afterward. Every source observation rereads the Git inventory and repository metadata, checks each selected file, and verifies all observed file identities again after the inventory comparison. New paths, removals, inode replacements, same-size writes with restored mtime, and edits during observation therefore invalidate the observation or require new bytes. Each observation verifies unique parent-directory real paths and rechecks them at the end; symbolic-link files also recheck containment before reuse. Final source witnesses compare both the leaf lstat identity and the followed target identity, so retargeting a link to a preexisting hardlink cannot bypass the end-of-observation check. Unchanged dangling links remain absent; newly appearing targets invalidate the observation. Changed files undergo real-path containment checking before reading. Lens, note and draft text reads have pre/post/final identity witnesses; absent, nonfile and oversized selected paths retain final observation witnesses. Concurrent observations share verified byte records but keep separate verification sets. No unresolved path is read from outside the repository. A missing input follows existing missing-file handling; changes during a scan fail closed and the next query retries.

Unknown filesystems, cross-device source files and coarse whole-second ctime values use full byte reads. Artifact files also have an initial full digest, descriptor and path checks, and the same local-filesystem witness constraints. These are ordinary local-filesystem guarantees, not protection against a privileged process forging filesystem metadata or a filesystem that misreports its type/change times. Remote filesystems never use the fast path. Synchronous builds and historical observations retain their full-content path.

## Profiling evidence

On the frozen large L9 source tree, Node25.8.2/macOS, an unchanged full observation took7509ms, including4692ms in49,528 synchronous file reads and846ms in49,606 real-path resolutions. A separate run took8557ms. This is source observation alone, excluding graph artifact verification, query work and response serialization.

A preliminary witness implementation took3976ms cold and1934/2434ms warm. Resolving containment only when reading new bytes reduced preliminary warm observations to1152/1265/1702ms. These intermediate figures precede the final cross-observation identity pass and are **not** the thirty-request MCP p95 acceptance measurement. The final cross-observation pass measured1332/1253/1230ms for source observation alone. A CPU profile attributed most remaining time to Git subprocess waits and metadata checks. Omitting the redundant immediate post-stat for cached bytes while retaining the final global pass subsequently measured1013/973/973ms; cold was6812ms during concurrent development. Subsequent alias/configuration/absence race fixes add containment checks; these intermediate numbers do not establish the one-second gate. The final all-repository client timings remain required.

Regression coverage includes same-size/restored-mtime source and artifact edits, path replacement and deletion, invalid lens failure/recovery, concurrent cold build-once, graph/presentation generation invalidation, and source changes both during byte reads and after an individual file was observed. Existing source additions/removals remain covered by the MCP integration test.

## Streaming validation and overlapping observations

Stored graph records are schema-decoded one at a time. Identical complete source records and ordered source arrays share immutable storage within that read; revision and URL remain part of the sharing identity. Canonical graph validation and hash verification still run over every record. A repeated-evidence fixture containing 1,000 nodes and 300,000 source entries fails the former reader under a 64MiB heap and loads with the same hash under the streaming reader. This avoids retaining the complete raw document alongside its decoded copy.

Git inventory uses cached paths plus porcelain-v2 untracked entries. Rename records' second filenames are skipped. Separate scans limited to the generated cache/site scopes preserve paths excluded from the status command. Both before/after Git observations still execute; no Git metadata is cached as proof.

After a successful observation, its metadata and path inventory may serve as a speculative selection hint while the next before-Git command runs. The speculative read uses a new verification context. If the fresh Git result differs, its entire result or error is discarded and current inputs are observed again with another context. The after-Git comparison and final source, configuration and containment witnesses run after the fresh before-Git result has been accepted. Only complete success updates the hint. Default lens candidates, note-directory membership and draft-file paths carry final presence/absence and identity witnesses, including Git-ignored configuration. Creating, removing or renaming these paths during observation therefore cannot bypass verification merely because Git inventory is unchanged. Cold requests cannot overlap this way. Same-size/restored-mtime edits during the pending Git command, note/lens changes, inventory changes and discarded speculative failures have regression coverage.

The first large-tree MCP diagnostic after streaming validation completed without the former default-heap OOM. Cold response took 203.8s, including full snapshot verification/build/persistence; warmed queries remained dominated by source observation. Its 30-request p95 was 2.075s and failed the gate. A two-second diagnostic CPU profile overlapped that warm run, so it is not a final acceptance measurement. The failure and profiler intervention remain recorded; subsequent optimizations require an unprofiled final client campaign.

After the overlap and configuration-presence fixes, a separate unprofiled source-only run (5 preparation observations followed by 30 measured observations) recorded p95 955.254ms, median 916.710ms and maximum 957.755ms. Every fingerprint matched. This isolates freshness cost and does not include resident graph pressure, MCP query work or serialization; it is not the final MCP acceptance result.

## Rejected resident-graph experiments

The following core-interner and initialization-order variants were measured and then removed; the selected implementation retains the earlier streaming reader and speculative observation overlap.

The subsequent unprofiled resident-graph diagnostic recorded cold preparation 181.688s and warm p95 1,497.229ms (median 981.371ms, maximum 8,947.868ms), with all 30 responses fresh, no errors and unchanged source/generated implementation fingerprints. It still failed the one-second gate. Saved phase timings attributed the large outliers to observation rather than graph queries. Complete provenance interning was consequently moved into the shared graph construction path as well as the streamed reader: the experimental newly built resident graphs shared equal source objects and ordered arrays, while retaining revision, URL, order and multiplicity. The per-construction clone preserves caller isolation and immutability. This change requires another actual MCP measurement; reduced allocation alone is not acceptance evidence.

The first core-interner diagnostic failed during cold preparation with default-heap exhaustion before any response. That attempt retained both a replacement record collection and per-original-source canonical-key caches during cloning. The revised clone interns each source when copying an individual record, omits the intermediate whole graph and releases construction dictionaries before hashing. The OOM attempt and its verified dead-writer-lock recovery remain recorded separately; this revision also needs real default-heap validation.

A standalone default-heap phase probe then loaded and validated the same graph successfully: heap usage was 3.020GB after streamed decoding, 2.747GB before cloning, 3.811GB after cloning and 3.667GB on return, with an identical graph hash. The revised MCP attempt still exhausted the heap because source text was already resident during snapshot validation. The experimental initial asynchronous preparation validated snapshot history before observing source text, then rechecked the prepared catalog and all artifact digests under the publication lock. A changed catalog during observation rejects the query; failed initial observations publish no current graph. Warm queries retain their existing order and checks. This ordering change has no heap-limit override and requires another full default-heap diagnostic.

The final ordering experiment completed without errors under the default heap, but cold preparation increased to 380.255s and warm p95 remained 1,550.570ms (median 1,025.611ms, maximum 1,587.789ms). Source and generated implementation fingerprints were unchanged during the run. Because this did not improve the acceptance gate and roughly doubled cold cost, the core interner, its construction changes and the initial ordering change were removed along with their experiment-only tests. The selected stable path retains the earlier 181.688s cold / 1,497.229ms p95 diagnostic as a failure; formal candidate measurement remains required and the one-second gate must not be reported as passed.
